# Spike C1: justified layout + TanStack Virtual at 50k

**Question.** Can the prototype's justified-row algorithm, ported as a pure module and driven by
TanStack Virtual, meet the plan §9 budgets at 50k items? The budgets are a layout in 50 ms or less, and
no long task over 50 ms while scrolling. Do focus pinning and resize anchoring work, or do we need
another library or a chunked collection?

**Setup.** The code is in `client/src/media-manager/test/spikes/c1/`:

- `justifiedLayout.ts`: the pure module. It ports `grid.js` `justifiedRows` and `data.js` `aspectRatio`
  over the flat stride-4 `CollectionResponse.rows`. It writes into typed arrays and creates no
  per-item objects.
- `syntheticCollection.ts`: seeded 50k/100k rows with a realistic mix of kinds and sizes, 3 % of them
  with an unknown size.
- `VirtualJustifiedGrid.tsx`: the spike component.

The pure module was measured in Node. The component was measured in headless Chromium (Vitest browser
mode, 1000×700 viewport, plain tiles without images).

Run it: `npx vitest run src/media-manager/test/spikes/c1 --reporter=verbose` in `client/`. The logged
`[C1]` lines are the numbers below.

## Results

| Measure | Result | Budget |
|---|---|---|
| Layout of 50k items in Node, at 390/1264/2520 px × densities 120/200/340 (medians) | 1.3–2.2 ms | ≤ 50 ms |
| Layout of 100k items in Node, same matrix | 2.5–3.6 ms | — |
| Layout of 50k items in Chromium, at 390/1000/2520 px × all 5 densities | 1.1–4.4 ms | ≤ 50 ms |
| DOM at 1000×700, density 200 | 7 rows, 24 tiles mounted (overscan 3) | — |
| Scrolling 400 steps over the 1.98M px grid: 300 one-viewport steps, then 100 jumps like scrollbar drags | Each step renders in one frame (p50 16.7 ms, p95 ≤ 18.3 ms, max ≤ 24 ms). **0 long tasks** | none over 50 ms |
| Focus pinning: focus a tile, scroll to the end | The tile stays mounted and focused. ↓ from it moves focus and scrolls back | — |
| Resize anchoring: 1000 → 760 → 1280 → 1000 px with a focused tile; 1000 → 700 px without focus | The anchor tile stays within 1 px of its viewport position, and focus is kept. 0 long tasks | — |

In the `dev/run test unit` runner (Docker), the same tests pass: 50k layout takes 2.2–4.3 ms in Node
and 1.8–7.0 ms in Chromium, and scrolling again gives 0 long tasks with a p95 of 17.0 ms.

The unit tests also check that every full row sums exactly to the container width at 50k, the last row
isn't stretched, panoramas, unknown sizes and kinds, the ↑/↓ neighbour rule and edge cases.

## Decision

**Keep TanStack Virtual and the ported algorithm.** Both budgets are met with a margin of 10× or more.
There's no need for a library swap or a chunked collection for layout or scrolling. (Payload and parse
time are spike C5, track F2.)

## Gotchas (A1 must handle these)

1. **Call `virtualizer.measure()` after every re-layout.** TanStack Virtual doesn't notice a change of
   `estimateSize` on its own.
2. **Restoring the anchor needs an explicit scroll event.** Setting `scrollTop` in the re-layout's layout
   effect fires *no* `scroll` event in Chromium, because the content height changes in the same frame.
   TanStack Virtual then keeps rendering the old range. Dispatch `new Event('scroll')` after setting it.
3. **The focused tile is re-created after a re-layout.** Rows are keyed by index and their items change,
   so the tile remounts and focus drops to `<body>`. Re-focus the tile with `preventScroll` once it is
   rendered again. The spike does this in a layout effect.
4. **Use a native passive scroll listener for anchor tracking**, rather than React state per scroll
   event.
5. **Set `scrollbar-gutter: stable`** on the scroller, so a scrollbar appearing never changes the layout
   width.

## What A1 should lift

- `justifiedLayout.ts` as is:
  - `computeJustifiedLayout`, `aspectRatio`, `DENSITIES` and `GRID_GAP`;
  - `rowOfItem` and `firstRowBelow`;
  - `verticalNeighbour` (↑/↓);
  - `withPinnedIndex`, which wraps `defaultRangeExtractor` to pin the focused row;
  - `captureScrollAnchor`, `scrollTopForAnchor` and `scrollTopToReveal`.
- Its unit tests in `justifiedLayout.spec.ts`.
- The component's wiring:
  - rows sized `rowHeight + gap` (none after the last row), overscan 3;
  - tiles positioned absolutely from `itemX` and `itemWidth`;
  - the anchor updated on scroll and on focus, and restored before paint after a re-layout;
  - keyboard focus moves with `focus({preventScroll})` plus `scrollTopToReveal`.

The browser spec's long-task and frame-time harness can become the `perf` checks.

## Limits

- The timings are from headless Chromium on a developer machine, with plain tiles and no images. Image
  decoding is a separate cost: lazy `<img>`, sized sub-sizes.
- The scroll steps are programmatic, one per frame. Real wheel and touch scrolling and other engines
  (Firefox, WebKit) still need checking. Spike C2 (F1) runs Playwright across engines.
