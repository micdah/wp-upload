# Spike X5: `include=` hydration of 100 items with `_fields`

Track S1, M1. Question (implementation plan §10): does hydrating the grid's chunks through core's
`GET /wp/v2/media?include=<100 ids>&_fields=…` (plus the plugin's `wpu` field) stay under 500 ms, or
does the server need a plugin `tiles` route?

## Result: keep `include=` hydration. No plugin `tiles` route

| Request (100 items, shuffled ids, `context=view`, `status=inherit,private,trash`, `orderby=include`) | Body | Median | p95 |
|---|---|---|---|
| Tile fields, core only | 28 kB | 36 ms | 53 ms |
| Tile fields + a naive `wpu` field | 83 kB | 61 ms | 75 ms |
| Full-view fields (`media_details`, `link`, `post`, `_links`) + naive `wpu` | 268 kB | 130 ms | 162 ms |
| No `_fields` at all + naive `wpu` (for comparison) | 398 kB | 188 ms | 230 ms |
| `GET api/library/items?ids=<100>` through the server (guard, rev, normaliser) | — | 98 ms (one run, cold cache) | — |

30 runs each after a warm-up, timed from the host against `dev/run up dev` + `seed small` (211
items, WordPress 7.1.5, PHP 8.3, MariaDB 11.4, FileBird 6.5.9). The live spec
`server/src/lib/library/wordpress.live.spec.ts` repeats the tile measurement on every
`dev/run test server-live` run (it measured a median of 87 ms through `wpAxios`) and fails above
500 ms.

**The naive `wpu` field** was a temporary mu-plugin (not committed; removed from the stack afterwards)
that reads, per item and without any priming, what P1's providers will read: attachment metadata, the
attached file's size (a `stat`), the FileBird folder (one SQL query per item), the author, the trash
meta, the original image path, `edit_post`/`delete_post`, and `wp_get_missing_image_subsizes()`. So
these numbers are an upper bound for P1's real field, which primes per page (plugin-api.md §7.2).
The same mu-plugin also stood in for `/info` and `/rev`, which let the real `items` route run end to
end: tile and full responses were valid against the zod schemas.

## Notes and caveats

- **Full view is 2–3× the tile cost**, mostly `_links` and `image_meta`. The client asks for it for
  the inspector and detail mode (a handful of ids), so it doesn't matter; grid chunks use `tile`.
- **Not measured yet:** the `large` seed (50k rows; track D's `seed large` isn't available) and the
  `test` stack's TLS proxy. `include=` cost grows with the ids asked for, not with library size (it is
  a primary-key lookup), so 50k shouldn't change this, but X4/perf should re-run the live spec there.
- **Re-check after P1 lands** with the real `wpu` providers: the live spec does it automatically.
- 100 ids make a URL of about 700 characters; no proxy limit is near.

## Facts about live WordPress 7.1 found on the way (the normaliser follows them)

1. `media_details.sizes` is stored in **generation order** (medium, large, thumbnail, medium_large,
   …), not registered order. The server sorts `sizes` by `/info`'s `imageSizes` order, which gives the
   fixtures' order (thumbnail, medium, medium_large, large, 1536x1536, 2048x2048, then `full`).
2. REST's attachment `link` is `?attachment_id=N` whether or not attachment pages exist
   (`wp_attachment_pages_enabled` is 0 on the stack, and the link 404s). `links.view` therefore needs
   a signal from the plugin (change request CR-S1-2 in the handoff note).
3. `_links["wp:attached-to"]` is present with `post_type`, `id` and `href`; `_fields=…,_links` works.
4. Every `self` link carries `targetHints.allow` (WordPress 6.7+), so one `context=view` read of the
   parent post tells whether the user may edit it.
5. `filename` (7.0+) is present; video `media_details` has `codec` (e.g. "H.264/MPEG-4 AVC") and
   `dataformat`; mp3 has only `dataformat` ("mp3"); `bitrate` is a float. SVGs come with
   `sizes: {}`, so the server builds their `full` entry itself.
