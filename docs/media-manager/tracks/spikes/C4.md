# Spike C4: one keymap dispatcher vs Mantine's key handling

**Question.** Does `installKeymap` layer correctly with Mantine Menu, Modal, Combobox, Popover and
Drawer, our own `useKeyLayer` layers and text fields, in Chromium, Firefox and WebKit? "Esc closes the
innermost layer first" (interaction-spec §5), and app keys pause in fields, modals, menus and listboxes
(§8).

**Setup.** `client/src/media-manager/app/spikes/c4/`: the real `installKeymap`, `DEFAULT_BINDINGS` and
`implementCommand`, Mantine 9.8.2, React 19, `<ConfirmHost/>`. `run-c4.mjs` sends real key presses with
Playwright 1.65.1 (Chromium 159, Firefox 159, WebKit 27.2, all in `wpu-runner:playwright-1.65.1`). It logs
every decision, which listener closed what (`window.event` phase and target), and what a fresh read at
bubble time would have decided. Each scenario runs against core and against the proposed changes
(`?patched=1`).

## Results

Each cell is core → patched. Chromium, Firefox and WebKit gave the same result except where noted.

| # | Scenario (detail mode unless noted) | Result | What happened in core |
|---|---|---|---|
| S1 | Menu opened by click; Esc, Esc | pass → pass | Esc 1: Mantine closes it (`onKeyDownCapture` on the dropdown) and focus returns to the trigger; we ignore it (`popup`). Esc 2: `detail.close` |
| S2 | Menu opened with Enter or Space | pass → pass | Same as S1. Mantine opens no Menu on ArrowDown, so ArrowDown stays an app key |
| S2g | **Grid mode**: Enter or Space on a focused button | **FAIL → pass** | Enter ran `detail.open` and Space ran `peek.toggle`. Our `preventDefault()` cancelled the button's own activation, so the menu never opened |
| S3 | Menu with `trigger="hover"` | pass → pass | Mantine moves focus into the dropdown even on hover (`trapFocus`), so it behaves like S1 |
| S4 | `confirm()` modal: `f`, Esc, Esc | **FAIL → pass** | `f` was ignored (`modal`). Esc was closed by Mantine's window capture listener, and we ignored it **only thanks to the capture snapshot**: a fresh read would have run `detail.close`. Fail: focus went to `<body>`, not back to the opener |
| S5 | Select or Autocomplete open; Esc ×3 | pass → pass | Esc 1: the Combobox closes from the input's React `onKeyDown`; we ignore it (snapshot; a fresh read would also have blurred the field). Esc 2: blur. Esc 3: `detail.close`. Typing `a` dispatches nothing |
| S6 | Our layer (peek), in grid mode; then a Menu inside it | pass → pass | Esc goes to the layer, not to `selection.clear`. Menu, then peek, then detail: each Esc closes one |
| S7 | Text field: `f`, Esc, Esc | pass → pass | `f` types. Esc blurs. Esc runs `detail.close` |
| S8 | `[data-mm-local-keys]` | pass → pass | ArrowRight is `ignore(local)` there and `detail.step` outside |
| S9 | Drawer: `f`, Esc, Esc | pass → pass | Mantine's window capture listener closes it, and focus returns to the opener. App keys stay paused until the drawer leaves the DOM: 283–306 ms after Esc (WebKit once took 686 ms) |
| S10 | Plain Popover, no layer: focus on the target / inside | FAIL → FAIL | Target: nothing handles Esc, and core swallowed it (`aria-expanded` trigger = `popup`). Inside: Mantine closes it **and** we run `detail.close`. Features must add a layer (S11) |
| S11a | Popover + `useKeyLayer`, focus on the target | **FAIL → pass** | Core swallowed Esc as `popup` before checking layers, so it was never closed |
| S11b | Popover + `useKeyLayer`, focus inside | **FAIL → pass** (Firefox: pass → pass) | Mantine closes it from the React capture handler. React then commits in the microtask before our bubble listener, so the layer was already gone and `detail.close` ran too |

Firefox passes S11b in core because under Playwright, React did not commit until after dispatch.
Juggler injects key events from privileged script, so no microtask checkpoint runs between
listeners. Real keystrokes are expected to behave like Chromium.

## Decision

Keep the **capture snapshot**. S4 and S5 show it is load-bearing in every engine: Mantine closes the
dialog or dropdown, and React re-renders before our bubble listener runs. Extend it to the top Esc layer,
and fix two context rules in `dispatch.ts`:

1. **Snapshot `topKeyLayer()` in the capture listener as well.** This fixes S11b. Calling a layer's
   close twice must be harmless (idempotent `setOpen(false)`).
2. **An expanded `aria-haspopup` trigger counts as `popup` only for comboboxes** (`role=combobox` or
   `aria-haspopup=listbox`, whose input handles Esc). Fixes S11a.
3. **New `control` context:** Enter and Space on a focused button, link, checkbox, switch, tab or menu
   item are `ignore('control')`. Fixes S2g. Grid tiles are `gridcell`s, so they keep Enter and Space.

Also fix `core/ui/confirm.tsx`: `ConfirmHost` unmounts the Modal the moment the request settles, so
Mantine's `returnFocus` never runs. Record the opener in `confirm()` and focus it again in the next frame
if focus fell to `<body>`. Keeping the Modal mounted through its exit transition would also work, but
then app keys stay paused about 300 ms, as in S9.

The proposed `dispatch.ts` passes the existing 53 keymap tests plus 2 new ones, run in the spike.

**What features must do**

- Mantine **Menu**, **Select**, **Autocomplete** and **Combobox**: keep the defaults (`closeOnEscape`,
  `trapFocus`, and Menu's `returnFocus`). Add nothing.
- **Modal** and **Drawer**: keep `closeOnEscape`, `trapFocus` and `returnFocus` on, so `aria-modal`
  pauses the keymap. Use `confirm()` for confirmations.
- **Popover** and **HoverCard** with focusable content: call
  `useKeyLayer(name, () => setOpened(false), opened)` and control `opened`. Leave `closeOnEscape` on
  and set `returnFocus`.
- Our own transient UI (peek, editor, drag): use `useKeyLayer`. Open nested layers one after another,
  not in the same render.
- A widget that owns arrows, Enter or Space and isn't a native control: wrap it in
  `[data-mm-local-keys]`.

## Remaining risks

- A Popover without a layer still breaks (S10). A dev-only warning, or a thin wrapper around `Popover`
  in core, would catch it.
- On macOS Safari, clicking a button doesn't focus it, so `confirm()` has no opener to restore. Its
  close button still returns focus there.
- App keys stay paused during a Drawer or Modal exit transition (about 0.3 s). This is fine for now.
  To tighten it, count an `aria-modal` only when it contains the event target.
- If an `aria-modal` is open before `installKeymap` runs, Mantine's capture listener runs before our
  snapshot. That is harmless as long as the modal stays in the DOM through its exit transition.
- The Firefox Playwright timing differs from real input (see S11b). The snapshot makes the result the
  same either way.
