# Spike X6: `POST /wp/v2/media?fbv=<id>` with an Application Password

Track S2, M1. Question (implementation plan §10): does FileBird file an upload into a folder when the
server sends `?fbv=<folder id>` with the media upload itself, so the separate `POST /folders/assign`
call after the upload can go?

## Result: it works, but the server keeps filing through the plugin's `POST /folders/assign`

**What happened.** Four uploads of the same small PNG to `POST /wp/v2/media` with the app user's
Application Password (`dev/run up dev` + `seed small`: WordPress 7.1.5, FileBird Lite 6.5.9, not in
per-user mode). Each row is the folder relation FileBird wrote:

| Query | `wp_fbv_attachment_folder.folder_id` afterwards |
|---|---|
| `?fbv=5` (an existing folder) | `5`: filed |
| `?fbv=0` | none: Uncategorized |
| `?fbv=9999` (**no such folder**) | `9999`: an orphaned relation |
| no `fbv` | none: Uncategorized |

**Why it works.** FileBird's `Classes\Core` hooks `add_attachment` on every request, REST included,
and reads `$_REQUEST['fbv']` there (`includes/Classes/Core.php:206-234`). Core's REST media
controller fires `add_attachment` through `wp_insert_attachment()`, after Application Password
authentication, so `get_current_user_id()` is the app user.

**Why we don't use it.**

1. **No folder check.** The handler only checks `FolderModel::verifyAuthor()`, which treats a
   missing folder as "created by user 0" and therefore allowed outside per-user mode. A stale folder
   id (deleted in another tab, or by someone else) files the item into a folder that doesn't exist:
   it then shows neither in Uncategorized nor in any folder. `POST /folders/assign` answers 404
   `wpu_folder_not_found` instead, and the upload reports `folder.assigned: false` with a message.
2. **Paths create folders.** A non-numeric value such as `3/Holiday` makes FileBird create the
   folder `Holiday` under folder 3 (`fbv_auto_create_folders`, on by default). The server only ever
   sends validated integers, but the plugin route has no such side door at all.
3. **One code path for filing.** Per-user mode (D10, skipped by the server anyway), the
   `wpu_forbidden` check and FileBird's own hooks all run the same way as drag-and-drop filing
   (plugin-api.md §10.3), and the plugin reports exactly what happened (`previous`, `skipped`).

The cost of the extra call is one small request per filed upload, after WordPress has already spent
seconds making sub-sizes. Briefly (between the two calls) the new item is in Uncategorized; the
client only sees the item once the job has `succeeded`, by which time it is filed.

**If we want it later:** send `?fbv=<id>` only for a folder id the server has just seen in the
plugin's `GET /folders` (cached per rev), and still fall back to `POST /folders/assign` when the
item came back in a different folder. Nothing in the contract changes either way
(plugin-api.md §10.4).

The test uploads were deleted again with `wp post delete --force`; FileBird's `delete_attachment`
hook removed their relation rows, including the orphaned one.
