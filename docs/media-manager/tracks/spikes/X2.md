# Spike X2: in-place image edits that keep the URL (D19)

**Decision:** our own `WP_Image_Editor` pipeline with backups (plan §8 fallback), not a shim around
`wp_save_image()` / `wp_restore_image()`. The item keeps its id **and** its file name, so the URL never
changes and `urlChanged` is `false` for every plugin edit. Implemented in
`plugin/wp-upload-companion/src/Images/{Engine,EditStack,Files,Lock}.php`.

## Why not the shim

`wp_save_image()` reads `$_REQUEST`, always writes a new `-e<timestamp>` file unless `IMAGE_EDIT_OVERWRITE`
is defined site-wide, combines operations its own way (`image_edit_apply_changes()`), and keeps only one
original. Overwriting in place with it would need a global constant and still leaves no undo stack.
A shim would be more fragile than the pipeline (about 1000 lines with replace and regenerate).

## How the pipeline works

1. Load the attached file (`-scaled` for big images, as wp-admin), apply its EXIF orientation, check
   the recipe against the size as each op changes it (`wpu_invalid_edit` before any pixel moves).
2. Apply the ops. Measured mapping (Imagick and GD agree): rotate clockwise `n` = `rotate(360 - n)`;
   `flipH` (left↔right) = `flip(false, true)`; `flipV` (top↔bottom) = `flip(true, false)`.
3. Save the result and every sub-size under **temporary names** in the same folder. Sub-sizes are named
   `<stem>-<w>x<h>.<ext>` with the stem the current sizes use (core: the unscaled original; wp-admin:
   its `-e…` file), so a size whose dimensions don't change keeps its URL too.
4. Before anything is overwritten, **hard-link** each existing target to a backup name
   (`-wpub<token>`; `copy()` where links fail). Then `rename()` the temporaries over the targets. A rename
   gives the file a new inode, so the hard link keeps the old bytes at zero disk cost.
5. On the first edit, the original is also recorded in WordPress's `_wp_attachment_backup_sizes`
   (`full-orig`, `<size>-orig`, pointing at `-wpuo<token>` links), so wp-admin's "Restore image" works.
6. The undo entry (`_wpu_edit_backups`, newest last, 10 max; older ones merge into the oldest so Restore
   still reaches the original) stores the metadata before, the backups, and a fingerprint of the state
   after. A fingerprint mismatch means wp-admin (or anything else) changed the item, and the stack is
   dropped instead of corrupting it.
7. `post_modified` is set with a direct update (not `wp_update_post()`, which would run kses over the
   text as the current user), then `wp_update_attachment_metadata()` fires the index hooks.

Undo renames the backups back and deletes only files that nothing references any more (current
metadata, remaining entries, backups, WordPress's backup sizes). Restore undoes every entry, then, if
the item had been edited in wp-admin before, calls core `wp_restore_image()` (that one changes the URL
back to wp-admin's original, reported as `urlChanged: true`).

## Results (dev stack, WordPress 7.1.5, PHP 8.3, Imagick with AVIF, GD with AVIF)

| Check | Result |
|---|---|
| Rotate/crop/scale recipe on JPEG, PNG, WebP, AVIF; Imagick and GD (forced) | Exact dimensions; sub-sizes regenerated |
| Undo, and Restore after 12 edits (with merges) | Byte-identical files, **same inodes**, no leftover files |
| `-scaled` image, all three `applyTo` targets | Main and sizes as specified; `nothumb` keeps the thumbnail; `thumbnail` changes only it (uncropped, as wp-admin) |
| Plugin edit, then wp-admin "Restore image" | Works (attached file becomes the recorded original copy); our stack goes stale and reports `undoable: false` |
| wp-admin edit, then plugin edit, undo, restore | Works; final restore goes through core and reports `urlChanged: true` |
| Delete after two edits | 41 files before, 0 left (WordPress deletes backup sizes, the plugin its stack files) |
| Two concurrent edits | One 200, the other 409 (`wpu_locked` or `wpu_stale`) |

## Limits and follow-ups

- **Animated GIFs** come out as one frame (as in wp-admin). Open question in the handoff note.
- A sub-size whose dimensions change (rotate 90°) gets a new name; the old file stays, with the old
  pixels, until undo/restore makes it current again or the item is deleted. Posts that embedded that
  specific sub-size URL keep showing the pre-edit image instead of a 404.
- Browser and CDN caches of the unchanged URL are the app's concern (`?v=<modifiedAt>`, D19).
