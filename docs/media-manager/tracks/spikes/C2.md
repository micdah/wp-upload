# Spike C2: the grid ↔ detail morph with a virtualised grid

**Question.** Does the shared-element morph (interaction-spec §5) work with a virtualised grid, including
the return to a tile that was never rendered (open #5, step 2,000 forward, leave detail), in Chromium,
Firefox and WebKit? Which strategy should core use?

**Setup.** Harness in `client/src/media-manager/app/spikes/c2/`: 50,000 items, TanStack Virtual
(`@tanstack/react-virtual` 3.14.27), 6 columns of 136 px rows, canvas images, a detail overlay over the
centre with the grid `inert` underneath. It uses the real `morph()` and `registerCenter()`.
`run-c2.mjs` (Playwright 1.65.1) runs in `wpu-runner:playwright-1.65.1` with headless Chromium
159.0.8154.6, Firefox 159.0 and WebKit 27.2, against Vite 8.3.8 dev at 1280×800. Screenshots and JSON are in
`test-results/spikes/c2/`. The strategies:

- **a**: reveal on exit with `scrollToIndex`, then poll rAF until the tile mounts.
- **a2**: reveal on exit synchronously. `flushSync` renders the target rows (a `rangeExtractor` unions
  pinned rows), then `scrollTop` is set directly.
- **b**: the inert grid follows detail (`scrollToIndex(row, {align: 'auto'})` on each step), so on exit `to`
  just reads the tile.

## Results (open #5 → step 2,000 → leave; exit transition)

| Engine | Strategy | Hero animated | Close → `finished` | `to` resolved | Tile in view | Errors |
|---|---|---|---|---|---|---|
| Chromium | a | **no**: `to` timed out | 798 ms | 526 ms | yes | 0 |
| Chromium | a2 | yes | 311 ms | 13 ms | yes | 0 |
| Chromium | b | yes | 312 ms | sync | yes | 0 |
| Firefox | a | **no**: `to` timed out | 785 ms | 524 ms | yes | 0 |
| Firefox | a2 | yes | 274 ms | 19 ms | yes | 0 |
| Firefox | b | yes | 291 ms | sync | yes | 0 |
| WebKit | a | yes | 377 ms | 34 ms | yes | 0 |
| WebKit | a2 | yes | 413 ms | 19 ms | yes | 0 |
| WebKit | b | yes | 369 ms | sync | yes | 0 |

Other scenarios behaved the same in all three engines:

- **Entry morph:** the hero animates.
- **Step and leave in one task:** same as the table.
- **Reduced motion:** no hero, root cross-fade only. With today's `morph`, a and a2 never reveal the tile
  (`to` is not called) and the grid stays at #5. b is fine.
- **No API:** same as reduced motion: a and a2 never reveal, b is fine.
- **The proposed `morph`** (`morph-proposed.ts`) fixes both cases for a and a2.
- **`content-visibility: auto` on rows:** a and a2 lose the hero, because a freshly mounted row is
  skipped and can't be captured. b keeps it.

**Why a fails.** While the update callback is pending, Chromium and Firefox run **no rAF and no scroll
events**: 0 frames and about 31 timer ticks in 500 ms. TanStack never updates its range, the screen stays
frozen on the old snapshot until the 500 ms timeout, and you then get a cross-fade without the hero. WebKit
does run rAF there.

## Decision

Core uses **b, backed by a synchronous `revealItem`** (a2's technique) as the exit `to`:

- While detail is open, the grid follows the current item, so the tile is normally already mounted and
  in view.
- `revealItem` covers deep links, a collection that changed while in detail, and a grid that hasn't caught
  up yet.
- Never use a reveal that waits for frames or scroll events (a).

**Fallbacks:** with no API, the update runs and then the reveal. Under reduced motion, the root cross-fades
and the reveal still runs. If `to` misses the timeout, the root cross-fades without a hero.

## Implications for core

- **`centerApi.revealItem(id)` contract:**
  - It does its DOM work synchronously and resolves without waiting for a frame, a scroll event or a
    ResizeObserver.
  - If the tile is fully in view, it returns the tile.
  - Otherwise it renders the rows for the target scroll position with `flushSync`, sets
    `scroller.scrollTop` itself, and returns the mounted tile, or null if the item isn't in the grid.
  - The grid clears the extra rows once the virtualizer's own range covers them.
  - F3's justified layout must expose the item's row offset without measuring.
- **The grid in detail mode** follows the current item with `scrollToIndex(row, {align: 'auto'})` in a
  layout effect, only when the row changes. It must stay laid out (`inert`, not `display: none`), and
  rows and tiles must not use `content-visibility: auto`.
- **Named elements:** name the tile's `<img>` and the stage image, and size the stage image to its fitted
  box (aspect ratio) so the hero doesn't stretch into the letterbox.
- **Entry:** only name `from` if the tile is fully inside the scroll container. Otherwise reveal it first,
  or skip the hero. View-transition pseudos aren't clipped by the scroller, so a half-hidden tile's hero
  paints over the toolbar (`*-a2-enter-clipped-mid.png`).
- **`morph` changes:**
  - Always call `to`, also under reduced motion and without the API, because it carries the reveal.
  - Lower the timeout from 500 to 150 ms, because waiting longer only freezes the screen in Chromium and
    Firefox. The diff is in the C2 report and in `morph-proposed.ts`.
- **Stacking:** `inert`, the overlay's z-index and scroll anchoring caused no problems. The hero paints
  above the overlay in every engine.

## Remaining risks

- Playwright's Firefox screenshots don't show the view-transition layer, even though the animations were
  paused mid-way. In Firefox the hero is verified only through `document.getAnimations()`.
- Real thumbnails: a tile a2 mounts on exit may not have loaded or decoded its image yet, so the hero
  would end on an empty box. b avoids this because the followed rows load while you're in detail.
- A long synchronous task just before leaving delays the old-snapshot capture. Firefox took 0.4–1 s after
  2,000 steps run in one 4 s task, which is a harness artefact.
- Not tested: real WordPress media, the justified grid (F3), and touch devices.
