# Spike C3: virtual folder tree + Pragmatic drag and drop

**Question.** Does the plan §3 choice for the folder column hold up? The choice is a custom flattened ARIA
tree, virtualised with TanStack Virtual, with Pragmatic drag and drop (hitbox, auto-scroll, and an
in-page preview with the native one disabled). Specifically:

- nest vs reorder hitboxes, and the cycle block;
- a live preview, auto-expand and auto-scroll;
- what happens when the dragged row is virtualised away;
- its cost at 300 folders (the `large` seed) and at 5k.

**Setup.** The code was in `client/src/media-manager/test/spikes/c3/` (deleted in the M3 integration, once A3 had lifted it into `features/folders/`):

- `folderTree.ts`: the pure model. It flattens folders into ARIA rows, decides which drops a row allows
  (including the cycle rule), resolves a drop to the API's `{parent, position}`, and applies a move
  optimistically.
- `seedFolders.ts`: seeded 300 and 5k trees, plus a small sample.
- `VirtualFolderTree.tsx` and its `.module.css`: the spike component.
- `dragDriver.ts`: a synthetic native-drag driver for tests.

It ran in headless Chromium in Vitest browser mode. Run it:
`npx vitest run src/media-manager/test/spikes/c3 --reporter=verbose` in `client/`.

## Results

| Behaviour or measure | Result |
|---|---|
| ARIA tree | `role=tree` / `treeitem`, `aria-level`, `aria-posinset`, `aria-setsize`, `aria-expanded`, one Tab stop (roving tabindex). → expands and ↓ moves focus. Passes |
| Hitbox (list-item `attachInstruction`) | Top quarter = reorder-before, with a line; middle = combine (nest), with a ring; bottom quarter = reorder-after. Passes |
| Open folder | Its bottom edge means "inside", because `reorder-after` is not available there. Passes |
| Cycle | Dragging a folder over its own descendant gives `blocked`: a danger outline, the preview says why, and the drop is refused. Passes |
| Live preview | An in-page element (the native preview is disabled) follows the pointer without a React render and reads "Move into / before / after …". Passes |
| Drop | Becomes the API's `{parent, position}`, and the optimistic `applyFolderMove` re-renders the tree. Passes |
| Auto-expand | A closed folder isn't open after 300 ms of hovering, and is open after 700 ms. Passes |
| Auto-scroll | `autoScrollForElements` scrolled 760 px in 1 s near the bottom edge. Passes |
| Media drop | A media draggable dropped on any part of a row means "into" (assign), with ids `[101, 102]`. Passes |
| Source row virtualised away mid-drag | Unpinned, the source unmounts and the drag and drop still complete. Pinned, it stays mounted. Passes |
| Flatten 5k folders, all expanded (Node) | 4.4 ms |
| First render, all expanded, 600 px tall | 300 folders: 10.4 ms. 5k folders: 13.1 ms. 28 rows mounted either way |
| Drag through 200 rows of a 5k tree, scrolling a row per step | **0 long tasks**. A step (2 frames) takes p95 34 ms |

In the `dev/run test unit` runner (Docker), the same tests pass: flatten takes 9.2 ms, renders 10.2 and
12.3 ms, the drag has 0 long tasks with a step p95 of 34.6 ms, and auto-scroll covers 760 px/s.

## Decision

**Keep the plan's choice: Pragmatic DnD with its hitbox and auto-scroll, TanStack Virtual, and the custom
tree.** Every behaviour works, and the cost is flat in the folder count, because only the mounted rows
register drop targets. Mantine `Tree` isn't needed.

## Gotchas

- **v4/v3 import paths:**
  - the documented entry points `@atlaskit/pragmatic-drag-and-drop/element/adapter`, `/combine` and
    `/element/disable-native-drag-preview`. The package has no `exports` map, so deep paths such as
    `adapter/element-adapter` resolve too; don't use them;
  - `@atlaskit/pragmatic-drag-and-drop-hitbox/list-item`, which gives `attachInstruction`,
    `extractInstruction` and the operation names `reorder-before`, `reorder-after` and `combine`. Its
    `Availability` values are `available`, `not-available` and `blocked`. A blocked zone still resolves,
    so the UI can say why;
  - `@atlaskit/pragmatic-drag-and-drop-auto-scroll/element`.
- **Drag data are records.** Type payloads as `Record<string | symbol, unknown> & {…}`, or the type
  guards don't compile.
- **`getData` runs on every dragover.** Read the row from a ref, so registrations survive re-renders.
  One monitor owns the drag state, and the visible state changes only when the target or operation
  changes.
- **A removed source gets no `dragend`.** Pragmatic still ends the drag on `drop`. Without a drop, it
  ends on the next `pointerdown`, or after 20 `pointermove`s (read from the library source). Pinning
  the dragged row in the `rangeExtractor`, as the spike does by default, avoids the problem entirely.
- **The Tab-stop row is always pinned too**, so focus never unmounts.
- **Testing:** synthetic `DragEvent`s with a `DataTransfer`, dispatched on the real elements, drive
  Pragmatic deterministically. That includes hovering in place, which Playwright's real mouse can't do,
  because Chromium only sends `dragover` while it moves. Wait one animation frame per step: Pragmatic
  calls `onDragStart` on the next frame and batches `onDrag` per frame. A probe confirmed that real
  Playwright drags (`userEvent.pointer`) also work in the Vitest iframe. Use those for a few end-to-end
  smoke tests.

## What A3 should lift

- `folderTree.ts` and its spec as they are:
  - `indexFolders`, `flattenVisible`, `ancestorsOf`, `isSelfOrDescendant`;
  - `folderDropAvailability`, `MEDIA_DROP_AVAILABILITY`;
  - `resolveFolderMove`, `applyFolderMove`.
- `VirtualFolderTree.tsx` as the starting point of the column's tree: the row registration, the
  monitor, the auto-expand timer, the preview and the root drop area. Add the spec's missing parts:
  context menu, inline rename, counts mode, Pro colours.
- `dragDriver.ts` for component tests.
- The media drag type `mm/media` with `{ids}`, which the grid's `useMediaDraggable` (F1) should emit.

## Limits

- Only headless Chromium was tested, with synthetic drag events.
- Real-pointer drag feel, Firefox and Safari, and touch still need a check in A3's e2e tests.
- The 700 ms auto-expand delay comes from the folders spec. It can be tuned in review.
