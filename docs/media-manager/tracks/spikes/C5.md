# Spike C5: the 50k collection payload

Track F2, M1. Question (plan §10): can the client take the whole ordered collection of a 50k library
as one `GET collection` (server-api.md §7.3), and what does the ETag revalidation path buy? If it
can't, the plan's fallback is a chunked collection.

## Method

- A deterministic generated library (`mocks/fake/generate.ts`, seed 20261122), shaped like a real
  WordPress library:
  - ids grow with the upload date;
  - 84 % images with 12 aspect ratios and long edges from 400 to 6000 px (big ones scaled to 2560);
  - the rest SVG, video, audio, documents and archives, with 0 × 0 for unknown dimensions.
- The response serialised exactly as the contract says: `rows` = `[id, w, h, kind] × total`.
- Measured with `node client/src/media-manager/mocks/spikes/c5-collection-payload.ts --browser`:
  - sizes: gzip level 6 (what the `compression` middleware uses) and brotli quality 4 (its default),
    plus other levels for comparison;
  - Node 26: medians of 15 runs;
  - Chromium (Playwright 1.65.1): a local server answering like the real one (gzip,
    `private, no-cache`, weak ETag, 304 on `If-None-Match`). Six loads per payload: the first, then
    five revalidations.
- Machine: i9-9900K desktop. Phones are roughly 4–6× slower on JSON work.

## Results

**Size of `GET collection` at 50k items (854 kB of JSON):**

| Sort | gzip 6 | gzip 9 | brotli 4 | brotli 5 | brotli 6 | brotli 11 |
|---|---|---|---|---|---|---|
| `date-desc`, `date-asc` | **235 kB** | 231 kB | 244 kB | 224 kB | 222 kB | 184 kB |
| `type-asc` | 238 kB | 236 kB | 252 kB | 236 kB | 233 kB | 183 kB |
| `dimensions-desc` | 213 kB | 209 kB | 218 kB | 207 kB | 207 kB | 142 kB |
| `size-desc`, `size-asc` | **262 kB** | 255 kB | 276 kB | 267 kB | 260 kB | 219 kB |
| `title-asc`, `name-asc` | **275 kB** | 267 kB | 289 kB | 281 kB | 273 kB | 231 kB |

- Compression time at 50k: gzip 6 takes about 40 ms, brotli 4 about 15 ms, brotli 5–6 25–35 ms,
  gzip 9 about 150 ms, and brotli 11 about 1.5 s.
- **100k, `date-desc`:** 1.7 MB of JSON, 472 kB with gzip 6.

Ids in date order are nearly sequential, so they compress well. Sorting by title or name scatters
them, and the payload grows by about 17 %.

**Client cost at 50k (`date-desc`, Chromium):**

| Step | First load | Revalidated (304) |
|---|---|---|
| `fetch()` until headers | 2.5 ms | 1.3 ms |
| `response.text()` | 4.3 ms | 4.3 ms |
| `JSON.parse` | 2.6 ms | 3.9 ms |
| `Uint32Array.from(rows)` | 0.3 ms | 0.5 ms |
| id → index `Map` | 4.2 ms | 2.7 ms |
| **Total** | **13.9 ms** | **12.7 ms** |

- **Node 26, 50k:**
  - `JSON.parse` takes 2.6 ms, the `Uint32Array` copy 0.6 ms, and the position map 3.0 ms;
  - removing 100 ids optimistically (`withoutIds`) takes 4.3 ms.
- **At 100k,** everything roughly doubles: 18–25 ms in total in Chromium.
- **The server saw** one full response and five 304s per payload: the browser sends
  `If-None-Match` by itself for `private, no-cache`, and hands the cached body to JavaScript as a
  normal 200.

**The fake at 50k** (mock mode, Node):
- `collection` answers in 15 ms (date) to about 150 ms (title sort, or the first search, which fills
  the search-text cache);
- `facets` takes 40–130 ms (the first call warms the month cache);
- 100 tiles take about 5 ms.

## Decision

1. **Keep one `collection` payload. Don't chunk it.** Parsing and indexing 50k rows costs about
   14 ms on a desktop, an estimated 55–85 ms on a mid-range phone. That is one task per collection
   load, which only happens on a new query or a new rev. Chunking would add requests and ordering
   complexity for no real gain.
2. **The client keeps the rows as a `Uint32Array`** (`core/data/collection.ts`). The copy is
   nearly free, and it needs half the memory of a `number[]`. The id → index map is built lazily on
   first use (`positionOf`), so a collection that is only rendered never pays for it.
3. **The ETag path saves bytes, not CPU.** A 304 still costs JavaScript the full read and parse
   (about 13 ms). In practice it rarely fires during a session:
   - the client refetches `collection` only after a rev change, and the rev is part of the ETag;
   - it helps on page reloads and when a query comes back after garbage collection (5 minutes),
     both without a rev change.

   So no client work is needed for it: don't send `If-None-Match` by hand.
4. **The 250 kB gzip budget (plan §9) holds for the default sort** (235 kB) and for the date, type
   and dimension sorts. **It does not hold for the title, name and size sorts** (262–275 kB). No
   practical compression level fixes that: brotli 11 does, but costs 1.5 s per request.
   Recommendation for the orchestrator:
   - restate the budget as "≤ 250 kB for the default sort, ≤ 300 kB for any sort at 50k"; and
   - optionally, have S1 configure brotli quality 5 for `api/library` (`compression({ brotli: …})`).
     That costs about 10 ms more CPU per 50k response than quality 4, and saves 8–20 kB on most
     sorts.

   Nothing in the contract changes.
5. **Long-task watch.** At 100k on a slow phone the load could pass 50 ms. If M5's measurements
   show that, the cheapest fix is client-side:
   - parse in a worker (`response.arrayBuffer()` → worker → transfer the `Uint32Array`);
   - or build the position map in idle slices.

   Neither needs a contract change, so this stays open until real devices are measured.

## Not measured

- Real devices (phones), and the real server's `compression` output. S1's server-live suite can
  check the bytes once `collection` is live.
- A real 50k WordPress library (D's `seed large`, spike X4); the generator only approximates its
  id and dimension distribution.
