# Spike X4: collection, facets and Uncategorized at 50k (track P1)

**Question:** do the plugin's `/collection`, `/facets` and the Uncategorized query meet plan §9
(p95 ≤ 300 ms at 50k attachments; collection payload ≤ 250 kB gzip)?

**Decision:** yes, with the denormalised `wpu_media_index` the contract already specifies. No
chunked collection is needed at 50k. One change came out of the spike: the Author visibility check
now uses a correlated `NOT EXISTS` (commit `perf(plugin): …`), which brought an Author's `/facets`
from p95 326 ms down to 246 ms.

## Setup

Track D's `large` seed isn't on P1's base yet, so P1 built a comparable profile in its own `dev` stack:

- **Data:**
  - 50 000 attachments: the 211 `small` items, plus rows and meta cloned from them, sharing their
    files, with dates spread over seven years;
  - about 60 % with alt text;
  - 300 FileBird folders made with `Folder::newFolder()`;
  - 35 000 items (70 %) assigned with `Folder::assignFolder()`.
- **Not included:** D's 5 000 posts. They don't affect these routes until the usage index exists.
- **Stack:** WordPress 7.1.5, PHP 8.3, MariaDB 11.4, no object cache, on a local workstation.
- **Measurement:**
  - times are over HTTP from the host, including WordPress's bootstrap (about 15 ms; see `/rev`);
  - each figure covers 20 runs.
- **Rerun:** D's `perf` suite should repeat this on the real `large` seed and in CI.

## Findings

- **Budget met** for every measured request: date sort, filters, Uncategorized, a single folder,
  facets and the folder tree, both as Editor and as Author.
- **Payload:**
  - At 50k the collection is 224 kB gzip, under the 250 kB budget but with little headroom.
  - Above roughly 55k items it will exceed the budget. The contract's hard limit is 250 000 rows
    (422 beyond).
  - If F3's spike C5 shows that parsing is the problem rather than size, nothing changes here.
    Otherwise chunking the collection is the plan §10 fallback.
- **Heaviest requests:** title sort and search. Both join `wp_posts` (title sort orders by
  `post_title`; search does LIKE on title, caption and description). They are within budget, but
  search grows with content size.
- **Author visibility:** the cost is the PK join to `wp_posts` for `post_parent`. If it ever matters,
  a `parent` column in the index (internal, no contract change, §8) removes the join.
- **No FileBird table scans:** in shared mode, folder filters and folder counts read only
  `wpu_media_index.folder_id` (index `status_folder`). Per-user mode reads FileBird's relation table
  (read-only). It is unmeasured at 50k but uses the same query shape FileBird itself uses.
