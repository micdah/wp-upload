# Track F2 (M1): client data layer and mocks

Follows the rules in [README.md](README.md).

**Goal:** everything the client needs to talk to `/api/library/*`, and a stateful mock backend, so every
client track can work without WordPress. Plan §3–§4; contract
[server-api.md](../contracts/server-api.md).

**You own:**
- in `client/src/media-manager/`: `core/data/**` and `mocks/**` (except the per-feature
  `mocks/handlers/<feature>.ts` files: keep them as the feature tracks' extension points, and register
  them in your collector);
- `client/vite.mock.config.ts` (the `VITE_MOCK` build);
- your handoff note `F2-handoff.md`.

**Deliverables:**
1. **`core/data`:**
   - `http.ts` over the existing `apiFetch` (relative `api/library/...` URLs only; a 401 triggers the
     existing session-lost flow);
   - query keys and TanStack Query setup;
   - hooks for bootstrap, rev polling, collection rows (stride 4), item chunks by id (100 or fewer, with
     `setQueryData` seeding), facets and folders;
   - one central `invalidate.ts` map keyed by `rev`;
   - optimistic-update helpers with rollback;
   - client-side chunking with progress for bulk mutations (D24).
2. **The mock backend:**
   - a stateful fake library seeded from `docs/media-manager/design/prototype/data/*.json` plus a 50k
     generator;
   - MSW handlers for every server route, each validated against the zod schemas in `shared/`;
   - scenarios from interaction-spec §11 (`normal`, `pro`, `per-user`, `no-filebird`, `no-plugin`,
     `author`, `trash`, `offline`, `loading`, `empty`), plus every `plugin.state`, chosen with
     `?mock-scenario=`.
3. **The mock build:**
   - `VITE_MOCK=1` builds via `vite.mock.config.ts` into `dev/.build/mock-dist/` (CR-6 in the M0 D
     handoff);
   - MSW's worker is copied into that build only, never into `client/public`;
   - the production build must contain no MSW (F3 adds the guard).
4. **Spike C5:** the 50k collection payload. Measure parse time and the ETag revalidation path.

**Contract tests:** one suite runs the same request/response checks against the fake **and**, via
`server-live`, against the real server, so mock and live can't drift.

**Tests:** Vitest for the data layer (optimistic rollback, membership removal, chunk seeding, 401
pause/resume) and the fake (schema validation of every response).
