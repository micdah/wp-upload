# Track S2 (M1): server, mutations, jobs and uploads

Follows the rules in [README.md](README.md).

**Base:** branch `mm/s2` from **`ecc1eab`** on `mm/s1`. That commit is S1's plugin client and error
mapping with their final signatures. Using it lets S2 start before S1 is merged. S1 merges first, then S2.

**Goal:** the Express side of [contracts/server-api.md](../contracts/server-api.md) for writes, jobs and
transfers:
- `items/batch` and `items/delete`;
- the trash routes and `usage`;
- the image operations as jobs: `items/:id/edit`, `edit/undo`, `restore` and `replace`, plus
  `items/regenerate`;
- `jobs`;
- `upload`, `upload/jobs` and `upload/check`;
- `posts`;
- `items/:id/download`;
- `plugin/download`.

**You own:**
- `server/src/routes/library/{batch,delete,trash,usage,images,jobs,upload,posts,download,pluginDownload}.ts`;
- `server/src/lib/library/jobs.ts`;
- `server/src/lib/library/normalise/<area>.ts` for your areas;
- the `fileInto` strategy hook in `server/src/lib/uploadJobs.ts`. Keep the legacy upload page working
  until M5;
- your specs and `*.live.spec.ts` files;
- your handoff note `S2-handoff.md`.

**Also allowed:** fix the scaffold's route path for regenerate. The contract says `POST items/regenerate`,
but the scaffold registered `POST /regenerate`. Fix it in your `images.ts` and in the matching row of
`server/src/routes/library/index.spec.ts`.

**Not yours:** S1's files (`index.ts`, bootstrap, rev, collection, facets, items, folders,
`pluginClient`, `cache`, `errors`, `normalise/{items,folders}.ts`, `specSupport.ts`), `app.ts`, the
Dockerfile, and `package.json`. Use S1's exports; ask for changes in a change request.

**Reuse from S1.** Read S1's handoff with `git show mm/s1:docs/media-manager/tracks/S1-handoff.md`; it
lists what you can use:
- `hydrateItems()`, for job and upload results;
- `sendNoStore`/`serveCachedRead` and `requireFeature`;
- `sendUntilDone`, for `remaining`-id resends;
- `toLibraryError()`;
- `currentRev`, which updates automatically from plugin responses;
- the plugin-state guard, already applied centrally.

**Key rules:**
- **Jobs:**
  - Long operations (edit, undo, restore, replace, regenerate) answer 202 with a `jobId`.
  - The job registry is in memory, and shares the upload concurrency budget (`acquireSlot`/`releaseSlot`
    in `uploadJobs.ts`).
  - Job states are `queued | running | processing | succeeded | failed` (contract #37).
  - Only upload jobs can be cancelled.
  - Thumbnail generation can take minutes, so no short timeouts on those calls.
- **Bulk operations:** the client chunks them (D24). The server enforces the per-request limits and
  re-sends `remaining` ids.
- **Uploads:**
  - Stream them as the legacy path does.
  - Put the file in its folder through the plugin, or via `?fbv=` if spike X6 shows it works. Run X6
    against your stack and write `spikes/X6.md`.
  - The form field is `folder`.
- **Downloads** are proxied with `Content-Disposition` and never cached.
- **`plugin/download`** serves the bundled zip. Where the bundle lives is S1's CR-S1-4; read
  `WPU_PLUGIN_BUNDLE_DIR` the same way S1 does.

**Tests:**
- Route specs in the existing style, using `shared/fixtures/` and S1's `specSupport.ts`.
- Live specs against your `dev/run up test` stack. Each skips itself until P2's plugin routes exist, as
  S1's do.
- `npm run test -w server` must pass without a WordPress.
- `dev/run test unit` and `server-live` must pass.
